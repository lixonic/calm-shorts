# Google Play performance and optimization review

Reviewed **13 October 2026**, against source commit `8006efd` and the published **1.1.0 / version code 10** APK, release `apk-10-1`.

The app already has a suitable SDK target, small optimized Android code, and correctly aligned native libraries. The main improvement areas are hidden-state video resources, native-device performance measurements, and distribution of the large offline collection. This review does not certify runtime compliance: no Android device, emulator, or Play Console performance data was available.

## The new requirements

Google announced new technical-quality requirements on **26 August 2026**, with memory and code-optimization enforcement beginning **February 2027**. Runtime memory is evaluated using anonymous RSS plus swap, and a separate bitmap metric. Installed video files are not themselves anonymous memory. [Google's announcement](https://android-developers.googleblog.com/2026/08/app-quality-memory-optimization-secure-onboarding.html).

For the app category on a 4 GB device, the published P90 memory thresholds are **2 GB foreground** and **1 GB background**. Non-visible bitmap thresholds are **200 MB background / user-perceived service** and **400 MB cached**. Optimization, shrinking, and obfuscation must each reach **25%** where an app has **more than 10 MB of DEX code**. These are ceilings and applicability rules, not desirable engineering targets. [Technical-quality requirements](https://support.google.com/googleplay/android-developer/answer/17492799?hl=en).

## Findings and priority

| Area | Current evidence | Assessment / next step |
| --- | --- | --- |
| Runtime video memory | `PageView.builder` builds pages lazily. Only the current visible video plays, and controllers are disposed when widgets leave the tree. Backgrounding pauses playback, but a mounted player retains its initialized controller. | **Improve resource handling.** Release native decoders and buffers when the app stays hidden or receives memory pressure; preserve playback position, pause state, and mute state when recreating them. Short system overlays should not constantly destroy and reopen playback. Measure before selecting a grace period. |
| Poster / bitmap memory | Prepared JPEG posters are small; Flutter's default image cache can retain up to 100 MiB. There is no app-specific cache budget or hidden-state eviction. | **Improve the cache budget.** Start with a modest poster cache, such as 16–24 MiB, and release unused cached images when hidden. Treat this as a proposed budget to verify, not a Google requirement. Live image references and native/GPU allocations also need profiling. |
| DEX optimization | The APK contains **one DEX file, 1,725,160 bytes** uncompressed. Flutter 3.47.0's Gradle plugin enables release minification and resource shrinking with optimized ProGuard rules by default; this workflow does not disable them. | **No immediate optimizer change needed.** The current DEX is below the new 10 MB applicability threshold. Do not interpret Dart/native AOT code or video assets as DEX. Recheck size and Play's reported optimization coverage after dependencies change. |
| Target SDK | The packaged manifest reports **compile SDK 36, target SDK 36, minimum SDK 24**. | **Meets the current target requirement.** New submissions and updates require API 36 from 31 August 2026. [Target API policy](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en). |
| Native 16 KB support | Every packaged `.so` has a 16 KB-aligned ZIP payload. Both ARM64 libraries have 64 KB-aligned ELF load segments. `extractNativeLibs` is false. | **Binary checks pass.** Add an APK alignment check to CI to detect regressions, and test install/playback on a 16 KB Android environment. Google's current guide states an update deadline of **1 February 2027**. [Page-size compatibility guide](https://developer.android.com/guide/practices/page-sizes). |
| Startup and swipe rendering | Loading and initialization show feedback. Posters cover video initialization. Playback progress updates are isolated to a small widget. Existing tests cover playback ordering, lifecycle pausing, initialization races, and disposal. | **Measurement missing.** Benchmark cold launch, first playable frame, rapid swipes, and revisiting history on Android phones. Browser screenshots and widget tests do not measure hardware decoder latency or Flutter frame timing. |
| Battery / background work | No app background service, network downloader, or explicit wake-lock code was found. The merged APK does include `WAKE_LOCK` and `ACCESS_NETWORK_STATE` permissions from dependencies; it has no `INTERNET` permission. Listening controllers stop/dispose when inactive. | **Verify on a phone.** A permission alone does not prove a held wake lock. Check screen-off playback, actual locks, CPU activity, and a longer viewing session. Video-controller cleanup would also reduce retained resources. |
| Offline download size | APK: **556,813,895 bytes**. Current local media: **527,130,658 bytes**, including **521,562,738 bytes of videos**. The workflow publishes APKs, not a Play AAB. | **Resolve before Play submission.** The current collection likely exceeds the **500 MB base-module compressed download limit** after accounting for app code. Measure a device-specific AAB download with bundletool/Play Console. Reduce the media with quality comparisons, or use an **install-time asset pack** so playback can remain offline after installation. [Current size limits](https://support.google.com/googleplay/android-developer/answer/9859372?hl=en). |

The small poster files and 720 × 1280-or-smaller H.264 videos are useful existing optimizations. The feed retains catalog metadata and shuffled order, rather than loading all 334 videos into memory. Keeping every video available offline remains achievable; a large installed collection is a different issue from excessive runtime RAM.

## Device checks needed before claiming readiness

1. Test a release/profile build on a lower-memory Android phone and a current Android phone, including a 16 KB environment. Capture CPU, decoder/buffer allocations, anonymous RSS plus swap, and bitmap/native memory while playing, swiping, hidden, and returning.
2. Run at least 100 rapid forward swipes and repeated backward swipes, then a full session. Verify native memory settles after disposal, sound never overlaps, and no decoder initialization or disposal errors appear.
3. Measure time to initial display and first usable video separately. Android vitals considers TTID excessive at **5 seconds cold, 2 seconds warm, and 1.5 seconds hot**. These are different from first-video readiness. [Startup metrics](https://developer.android.com/google/play/vitals/launch-time).
4. Capture Flutter frame timing during swipes and prompt interactions; at 60 Hz the UI frame budget is about **16.7 ms**. The UI refresh budget does not require re-encoding the source videos to 60 fps. [Core app quality](https://developer.android.com/docs/quality-guidelines/core-app-quality).
5. Background/lock the phone during video initialization, video playback, and listening. Check for stopped playback, reduced retained memory, clean restoration, and background CPU/wake locks. Excessive non-exempt wake locks can affect Play visibility under the current policy. [Wake-lock quality update](https://android-developers.googleblog.com/2026/03/how-whoop-decreased-excessive-partial.html).
6. Use a Play internal-test AAB and pre-launch report, then monitor Android vitals. Current overall bad-behavior thresholds include **1.09% user-perceived crashes** and **0.47% user-perceived ANRs**. These field rates cannot be established from local tests. [Android vitals](https://support.google.com/googleplay/android-developer/answer/9844486?hl=en).

For Play delivery, also replace the current personal development signing fallback with a stable upload key and produce an AAB. The existing [build guide](BUILD.md) explains the signing setup. The upcoming sign-in restoration requirement is inapplicable to this app's current account-free design; adding an account system would require revisiting it.
